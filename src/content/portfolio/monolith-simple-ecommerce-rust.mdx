## Distributed Modular Monolith – Simple E-commerce

Distributed Modular Monolith Simple E-commerce is a modern e-commerce backend built with Rust.
This project tries to combine the simplicity of a monolith with the flexibility of microservices using the modular monolith approach.

That means all services are managed in a single **monorepo**, but separated into independent modules/services (`auth`, `user`, `role`, `product`, `order`, `email`) that communicate over gRPC. From the outside, the system still looks like a single unit because an API Gateway (Axum) serves the REST API to clients.

---

## ⚡ Core Architecture

- Modular Monorepo → all services in one repo, but still with clear domain boundaries.
* API Gateway → provides the REST API for frontend/mobile, as well as a load balancer for internal services.
- Service-to-Service → communication between services uses gRPC (Tonic) for speed & efficiency.
- Event Streaming → important events (for example a successful order) are sent to **Kafka** and then processed by other services (example: the `email worker`).
- Full Observability` → tracing, metrics, and logging are ready out-of-the-box with OpenTelemetry.

---

## 🔑 Key Features

### 1. **User Management & Authentication**

- Registration & login with JWT Authentication (access + refresh token).
- Email verification & password reset using tokens.
- Role-based access control (RBAC) with `user ↔ role` mapping.
- Redis is used to cache sessions/tokens for faster access.

### 2. **Products & Orders**

- Product CRUD (name, price, stock, etc.).
- Simple order processing: users can create orders, the system automatically calculates the total price.
- Product stock is automatically decremented when an order transaction occurs.
- Order events are published to **Kafka**, then consumed by the `email worker` to send notifications.

### 3. **Observability & Monitoring**

- Tracing → every request between services can be traced with Jaeger.
- Metrics → application performance (latency, throughput, error rate) is exported to **Prometheus.
- Logging → structured logs are sent to **Loki** and visualized through Grafana.
- OpenTelemetry Collector is used as the main hub of the observability stack.

### 4. Infra & Deployment

- Database: PostgreSQL (SQLx) for primary data.
- Caching: Redis for sessions/tokens.
- Message Broker: Kafka for the event-driven flow.
- Containerization: Docker & Docker Compose ready to use.
- Makefile: to simplify build, run, up/down service commands.
- sqlx-cli: for automatic database migrations.

---

## 🎯 Strengths of This Project

- Scalable → can run as a monolith (easy) or be split into microservices (large scale).
- Production-ready → includes authentication, logging, monitoring, and full observability.
- Developer-friendly → runs with Docker Compose with no complicated setup.
- Complete learning experience → great for developers who want to learn Rust backend with a modern ecosystem (REST, gRPC, Kafka, OpenTelemetry).

## 🚀 Getting Started Guide

### Prerequisites

*   [Rust](https://www.rust-lang.org/tools/install) (for local development)
*   [Docker](https://docs.docker.com/get-docker/) and [Docker Compose](https://docs.docker.com/compose/install/)
*   [sqlx-cli](https://github.com/launchbadge/sqlx/tree/main/sqlx-cli) (for local database migrations): `cargo install sqlx-cli`

### 1. Clone the Repository

```bash
git clone https://github.com/mamangrust/monolith-simple-ecommerce.git
cd monolith-simple-ecommerce
```

### 2. Environment Configuration

Create a `.env` file in the project root directory. This file is required for `docker-compose.yaml` and for running the project locally.

Example `.env` file contents:
```env
# PostgreSQL
DATABASE_URL="postgres://postgres:postgres@db:5432/monolith_example_ecommerce"

# Redis
REDIS_URL="redis://:dragon_knight@redis:6379"

# JWT Secrets
JWT_SECRET="your_jwt_secret"
JWT_EXPIRES_IN="1d"
JWT_REFRESH_SECRET="your_jwt_refresh_secret"
JWT_REFRESH_EXPIRES_IN="7d"

# Other configuration
RUST_LOG="info"
```
**Note:** For local development, replace the hostnames (e.g. `db`, `redis`) with `localhost`.

### 3. Running the Project

#### Option A: With Docker (Recommended)

This is the easiest way to run all services, databases, and observability tooling.

```bash
make up

docker compose up -d
```

To stop all services:

```bash
make down

docker compose down
```

#### Option B: Running Locally

This method requires you to run the database and other dependencies on your local machine.

1.  **Run the Dependencies:** Make sure you have PostgreSQL and Redis running locally.

2.  **Run Database Migrations:** Make sure the `DATABASE_URL` in your `.env` file points to your local PostgreSQL instance.

    ```bash
    sqlx migrate run
    ```

3.  **Run the Services:** You can run each service in a separate terminal window. For example, to run `apigateway`:

    ```bash
    cargo run -p apigateway
    ```
    
    To run the `auth` service:
    ```bash
    cargo run -p auth
    ```
    ...and so on for the other services (`user`, `product`, etc.).

## Technical Decisions & Trade-offs

**Modular monolith instead of full microservices**
Each domain (auth, user, role, product, order, email) is an isolated crate with its own gRPC API, but the whole system ships and deploys as one unit behind a single gateway. That buys real service boundaries and explicit contracts without the operational tax of independently deployed microservices. The cost is that some boundaries are ceremony at this scale: calling a function over the network is slower and more verbose than calling it in-process, and the proto definitions are extra surface to maintain. It is the right middle ground for exercising the pattern while keeping `docker compose up` as the entire deployment story.

**Tonic gRPC for inter-service communication**
Typed proto contracts make every internal call compile-checked on both ends, and HTTP/2 multiplexing keeps the hop cheap. The trade-off is iteration friction: changing a message means regenerating the prost code and updating every client, and a failing gRPC call is harder to inspect than a JSON payload. REST exists only at the Axum gateway, so the stricter protocol stays on the internal network where it pays off.

**Axum as the public REST gateway**
External clients get plain JSON over HTTP, and the gateway doubles as a load balancer in front of the internal services. The price is an extra network hop on every request plus a second framework to maintain. Concentrating authentication, routing, and client-facing concerns at one edge is worth it - the alternative is every client knowing the internal service topology.

**Kafka for order events**
Order completion is published to Kafka and consumed by the email worker, so checkout is never blocked on sending mail and the order service knows nothing about email. The cost is a stateful broker in the stack and at-least-once delivery, which forces consumers to tolerate duplicates. For an event-driven design lesson built into the domain, that complexity is the point.

**SQLx over a full ORM**
Queries are written as SQL and checked against the real schema at compile time, with sqlx-cli handling migrations. That catches broken queries at build time, which is exactly where an ORM without compile-time checking gives you nothing. The cost is less abstraction: no entity graph or relation API, so complex result mapping is manual and SQL strings live in the source.

**Observability from day one**
OpenTelemetry feeds Jaeger, Prometheus, and Loki, so a request crossing five services can be followed end to end. The stack is a heavy docker-compose footprint for a portfolio project and demands real learning time. But in a distributed design, debugging without traces and correlated logs is guesswork, so this is load-bearing infrastructure rather than decoration.
