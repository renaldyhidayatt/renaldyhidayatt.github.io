## 🛒 Project Description

This project is an **e-commerce application** built with **Fiber** ⚡, a lightweight and fast Go framework for the backend. It integrates two essential services:
1. **Midtrans** 💳 for payment processing.
2. **Raja Ongkir** 📦 for shipping services.

The application provides a seamless shopping experience with a clean and functional user interface, as well as an admin panel for managing products and orders.

### ✨ Key Features
- **Backend** 💻: Built with **Fiber** ⚡, enabling fast and efficient data processing.
- **Payment Integration** 💳: Uses **Midtrans** for secure transaction processing.
- **Shipping Service** 📦: Integrated with **Raja Ongkir** to provide reliable shipping solutions.
- **Frontend** 🖥️: Modern and responsive user interface.

### 🛠 Technologies Used
- **Backend** 💻: **Fiber** ⚡ (Go)
- **Payment** 💳: **Midtrans**
- **Shipping** 📦: **Raja Ongkir**
- **Frontend** 🖥️: **React.js** ⚛️, **Bootstrap 5** ⚙️, and **Tauri.js** 🦀

## Technical Decisions & Trade-offs

**Go + Fiber**
A single static binary with a tiny footprint, which suits an API server well. The trade-off is that Fiber is built on `fasthttp`, not the stdlib `net/http`: Koa-style middleware and speed, but different server semantics (e.g., HTTP/2 support) and an ecosystem that mostly assumes the standard library.

**GORM vs raw SQL**
GORM buys dev speed: associations, callbacks, and auto-migration. The costs are reflection overhead, opaque SQL generation (you need the logger to audit what it actually runs), N+1 risk on associations (deliberate `Preload`), and auto-migration being fine in dev but something you must not run in production.

**Outsourcing payment to Midtrans**
You don't build payment infrastructure: PCI compliance, many payment methods, and a sandbox for free. The cost is a dependency on someone else's SLA — and because payment success arrives asynchronously (webhook), the order must sit in a *pending* state that transitions on notification. That forces idempotent webhook handling (retries and duplicates) plus a reconciliation fallback for callbacks that get lost.

**RajaOngkir for shipping rates**
Instant per-route shipping cost without implementing carrier pricing — but a second external dependency (rate limits, API changes), and the rate fetched at cart time can be stale by order confirmation, so it gets re-validated at checkout.

**Tauri desktop shell around React**
Tauri's Rust shell ships a fraction of an Electron binary's size. The trade-offs: per-OS packaging and signing, and distributing an e-commerce storefront as a desktop app is a demo choice, not a distribution channel. The backend is a separate process, so its URL/CORS must be configured per platform.
