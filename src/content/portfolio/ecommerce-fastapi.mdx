# 🛒 Ecommerce FastAPI React

This project is an **e-commerce platform** developed using **FastAPI** for the backend and **React** for the frontend. FastAPI was chosen due to its high performance and its syntax similarity to Express.js.

## ✨ Features

- **FastAPI-based API** 🚀 – Provides a high-performance backend.
- **Frontend with React and Tailwind CSS** 🖥️🌊 – Modern UI with a responsive design.
- **JWT Authentication** 🔐 – Secure user authentication system.

## 🛠 Technologies Used

- **FastAPI** 🚀 – High-performance web framework for building APIs.
- **React.js** ⚛️ – Modern frontend library for dynamic UI.
- **PostgreSQL** 🗃️ – Relational database management system.

## ⚖️ Technical Decisions & Trade-offs

**FastAPI vs Django / Flask**
FastAPI gives you ASGI (true async), Pydantic-validated request/response models, and auto-generated OpenAPI docs for free — a good deal for a REST API. The cost: it's an API framework, not a full web framework, so you assemble auth, admin, and ORM wiring yourself (Django ships all three out of the box). For a headless backend in front of a React app, that's the right trade — you're not paying for web-page machinery you don't use.

**PostgreSQL for e-commerce**
An e-commerce domain (products, carts, orders, inventory) is squarely relational: order/stock changes must be atomic, or you oversell. ACID transactions and FK integrity are the payoff. The cost is a fixed schema — every catalog change is a migration, and it won't scale horizontally the way a document store can. At this data volume, that's a non-issue.

**JWT over session cookies**
JWTs are stateless: no server-side session store, so any replica can verify any request — clean for a horizontally scaled API. The honest trade-offs: a leaked access token is valid until it expires (no instant revocation without a blacklist or short expiry + refresh-token rotation), and claims are small — you can't store much in the token, so it just carries identity. The standard mitigation is short-lived access tokens + rotating refresh tokens.

**React SPA + Tailwind for the frontend**
A fully client-side app gives fast interactions and a clean component model; Tailwind keeps styling consistent without a CSS framework's abstraction layer. The costs: no server-rendered HTML, so SEO has to be handled deliberately (and a static SPA behind a headless API has two deployables + CORS to manage, instead of one). For a portfolio-scale storefront that's acceptable; a public high-traffic store would push toward SSR (Next.js) or a partial-island approach.

**Why FastAPI "feels like Express"**
The framework was chosen partly for the familiar mental model: route-driven handlers, dependency injection for auth/middleware, and minimal boilerplate — so the API reads the way an Express router would, but with strict request validation and typed responses underneath.
