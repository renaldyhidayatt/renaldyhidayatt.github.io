## 🧩 Project Overview

**Movie gRPC** is a lightweight **gRPC microservice** built using **Rust**, with **Tonic** for the gRPC layer and **Axum** as the HTTP gateway. The project demonstrates observability practices using **OpenTelemetry**, **Jaeger**, **Prometheus**, and **Node Exporter**, all running inside a **Dockerized** environment.

All movie data is stored **in-memory**, making it perfect for demos, testing observability setups, or learning about tracing and monitoring in microservices.

---

## 🔧 Key Features

- 🧠 **In-Memory Movie CRUD**  
  Manage movie records without any external database — data resets on restart.

- 🚀 **gRPC API with Tonic**  
  Built with `tonic`, a high-performance gRPC implementation in Rust.

- 🌐 **Axum HTTP Gateway**  
  REST endpoints, healthchecks, or service introspection via `axum`.

- 🐾 **Distributed Tracing with OpenTelemetry + Jaeger**  
  See request spans and traces for gRPC calls with full context propagation.

- 📊 **Monitoring with Prometheus**  
  Collect runtime and custom metrics from your gRPC service.

- 🖥️ **System Metrics with Node Exporter**  
  Track CPU, memory, and system-level metrics from the host environment.

- 🐳 **Fully Containerized**  
  All components — app, Otel Collector, Jaeger, Prometheus, Node Exporter — run inside Docker.

## Technical Decisions & Trade-offs

**Tonic for the gRPC layer**
Tonic is the mature Rust gRPC stack: tower middleware, HTTP/2 multiplexing, and servers and clients generated from proto files. The costs are Rust's learning curve, slower compile cycles, and a protoc codegen step in the build. For a service whose point is demonstrating high-performance RPC with proper tracing, those costs land exactly where the value is.

**In-memory storage instead of a database**
Movie records live in process memory, so the container starts in seconds and the demo never fights a migration. The honest cost: every restart wipes the data, there is no crash recovery, and nothing here is a persistence reference. That is deliberate — the project exists to showcase observability plumbing, not storage.

**Axum as an HTTP sidecar to the gRPC server**
Browsers, health probes, and curl speak HTTP, not gRPC, so a small Axum gateway on a second port exposes REST endpoints and service introspection. The price is two frameworks to maintain and response shapes kept in sync with the proto definitions by hand. For demo and tooling friendliness, the duplication is worth it.

**Observability from the first commit**
OpenTelemetry spans flow through the OTel Collector into Jaeger, while Prometheus scrapes service metrics and Node Exporter covers the host. On a CRUD demo this stack is heavier than the application itself, and every container is one more thing to run. But the traces are the product here: seeing a gRPC call's full span tree is what the project teaches.

**Contract-first API design**
The movie schema is defined once in protobuf and drives both the wire format and the generated code, so server and clients cannot drift silently. The trade-off is friction outside the gRPC world: you cannot poke the API with a browser, and ad hoc testing needs grpcurl or a generated client rather than plain curl against JSON.
