## Example Sea Query Tonic Payment Gateway

This project is an example implementation of a **simple payment gateway system** built with the **Rust** programming language. Its main goal is to illustrate how to design financial services with a **service-oriented** approach, efficient communication via **gRPC**, and **observability** support from day one.

---

## ⚡ Key Features

### 🔐 1. User Management

* User registration & login.
* User data stored in PostgreSQL.
* Session tokenization can be combined with Redis for performance.

### 💰 2. Balance Management

* Every user has a balance account in the database.
* Supports the following operations:

  * **Top-up** (add balance).
  * **Withdraw** (withdraw balance).
  * **Transfer** (between users, debit & credit in a single transaction).

### 📑 3. Transactions

* All financial activity is recorded in the **transaction history**.
* Supports querying transactions per user.
* Consistency is maintained with database transactions (SQLx).

### ⚡ 4. Performance & Communication

* **Client → Server** uses gRPC (bandwidth-efficient & fast).
* SQL queries are built dynamically with **SeaQuery**.
* **sqlx** as the query runtime, supporting migrations & connection pooling.

### 📊 5. Observability (Monitoring & Logging)

* Request, error, and latency metrics are sent to **Prometheus**.
* Request/response logs are sent to **Loki**.
* All data is visualized through **Grafana Dashboards**.

---

## 🎯 Project Strengths

* **Lightweight & Fast** → Rust + gRPC for a high-performance backend.
* **Scalable** → can grow from simple to complex (for example, adding fraud detection or notification services).
* **Modular** → clear separation between the public service (Client) and the business core (Server).
* **Observability-ready** → performance and logs can be monitored right away.
* **Great for Learning** → teaches the fundamental concepts of a **payment system**, **event-driven design**, and **observability** in Rust.

## System Architecture

This project is split into two main services:

1. **Client Service (Axum REST API)**

   * Acts as the **public gateway** for receiving requests from users.
   * Provides REST endpoints (HTTPS) so they are easily accessible by web/mobile applications.
   * Performs input validation before forwarding requests to the internal service.

2. **Server Service (Tonic gRPC)**

   * Handles all **core business logic**: registration, top-up, transfer, withdraw, and balance checks.
   * Communication between services uses **gRPC** for speed and efficiency.
   * Interacts with **PostgreSQL** as the persistent database and **Redis** as the cache.

3. **Observability Stack**

   * **Prometheus** for metrics (latency, error rate, request count).
   * **Loki** for centralized logging.
   * **Grafana** as the dashboard for visualizing metrics & logs.

-   **User**: Sends requests (for example, registration, transfer, top-up) through the REST API to the `Client Service`.
-   **Client Service (Axum)**: Receives HTTP requests, performs initial validation, and forwards them to the `Server Service` via gRPC calls.
-   **Server Service (Tonic)**: Receives gRPC calls, processes all business logic, interacts with the database (PostgreSQL) and cache (Redis), then returns the result.
-   **Database (PostgreSQL)**: Stores persistent data such as user information, balances, and transaction history.
-   **Observability**: Metrics from both services are collected by Prometheus, and logs are collected by Loki. Both can be visualized using Grafana.

## Technical Decisions & Trade-offs

**A monorepo split into a public REST edge and a private gRPC core**
One workspace holds two services: an Axum client that validates and forwards external requests, and a Tonic server that owns the money logic. The split enforces a real boundary - the edge never touches the database directly - while a single repository keeps the proto contracts and both services in lockstep. The cost is a network hop plus serialization on every call that a single binary would not pay, and two deployables to run even in development. At this scale that overhead is paid deliberately, to keep the separation honest.

**SeaQuery for dynamic queries, SQLx for execution**
Filters and query shapes are composed programmatically with SeaQuery instead of concatenated SQL strings, then run through SQLx's pool, with migrations handled by sqlx-cli. The benefit is injection-safe, composable queries; the cost is two query layers to understand and generated SQL that occasionally needs inspecting before you trust it. For a payment schema with many filtered list endpoints, the composability earns its keep.

**Tonic gRPC as the internal contract**
Protocol Buffers define the interface between client and server, so mismatches fail at compile time and payloads stay compact. The trade-off is workflow friction: contract changes mean proto regeneration in the shared crate, and debugging needs gRPC-specific tooling. Inside a monorepo the regeneration step is cheap, which is where this design is most comfortable.

**Axum and utoipa on the public edge**
The REST side speaks the HTTP and JSON that web and mobile clients expect, with OpenAPI documentation generated from the handlers. The cost is maintaining two views of the same operations - REST at the edge, gRPC in the core - and keeping the OpenAPI annotations truthful. Exposing REST externally while keeping the typed protocol internal is the standard shape for good reason.

**Redis in front of PostgreSQL**
Sessions and hot reads are served from Redis so the database is not hit for every token check. The trade-offs are cache invalidation and a second stateful service that can fail independently. At this traffic level Redis is more learning exercise than necessity - which is a fair thing for a project like this to be.

**Database transactions for money movement**
Transfers debit and credit inside one SQLx transaction against PostgreSQL, so a partial move can never be committed. The boundary of that guarantee is the single database: scaling writes eventually means distributing the transaction, which is a genuinely hard problem. One honest gap is retry safety - idempotency keys on the mutating endpoints - which this example does not implement.

## Usage

This project can be run locally or with Docker.

### Running with Docker (Recommended)

This is the easiest way to run the entire system, including the database and observability services.

1.  **Prerequisites**:
    *   [Docker](https://www.docker.com/get-started)
    *   [Docker Compose](https://docs.docker.com/compose/install/)

2.  **Steps**:
    *   Clone this repository.
    *   Copy `.env.example` to `.env` if present, or make sure the configuration in `docker-compose.yaml` is correct.
    *   Open a terminal at the project root directory and run:
        ```bash
        docker-compose up --build -d
        ```
    *   This command builds the *images* for `client` and `server`, then starts all services (including PostgreSQL, Redis, Prometheus, etc.) in the background.
    *   To stop all services, run:
        ```bash
        docker-compose down
        ```

### Running in a Local Environment

To run the services manually on your local machine.

1.  **Prerequisites**:
    *   Install [Rust](https://www.rust-lang.org/tools/install).
    *   Install [PostgreSQL](https://www.postgresql.org/download/) and [Redis](https://redis.io/docs/getting-started/installation/).
    *   Install `sqlx-cli` for database migrations:
        ```bash
        cargo install sqlx-cli --no-default-features --features rustls,postgres
        ```

2.  **Steps**:
    *   Clone this repository.
    *   Create a new database in PostgreSQL for this project.
    *   Copy `.env.example` to `.env` and fill in the environment variables, especially `DATABASE_URL` and `REDIS_URL`. Example:
        ```
        DATABASE_URL="postgresql://user:password@localhost:5432/payment_db"
        REDIS_URL="redis://127.0.0.1/"
        ```
    *   Run the database migrations to create the required tables:
        ```bash
        sqlx migrate run
        ```
    *   Open a new terminal and run the **Server Service**:
        ```bash
        cargo run --bin server
        ```
    *   Open another terminal and run the **Client Service**:
        ```bash
        cargo run --bin client
        ```
    *   Now the `Client Service` will run at `http://127.0.0.1:8000` (or according to your configuration) and is ready to accept requests.
