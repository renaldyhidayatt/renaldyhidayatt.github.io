## Project Description

The **Movie GRPC** project is a **CRUD** application for managing movies, built with **Golang and GORM**. The application uses **gRPC** for communication between services and is supported by observability tools including **Jaeger, OpenTelemetry (Otel), and Prometheus** for monitoring and tracing. All services run in a **Docker** environment for easy deployment.

### Key Features
- **Movie CRUD**: 🎬 Uses **GORM** 📦 as the ORM for database interaction.
- **gRPC Communication**: 🖧 The API is developed using **gRPC** for high efficiency and performance.
- **Observability**: 🐆 Implements **Jaeger** and 🌐 **OpenTelemetry (Otel)** for distributed tracing.
- **Monitoring**: 📊 Integrated with **Prometheus** for system metrics monitoring.
- **Containerized**: 🐋 All services are run within **Docker** for easier management and deployment.

### Technologies Used
- **Backend**: 🦸‍♂️ **Golang**, 🚀 **Gin**, 🖧 **gRPC**
- **Database**: 📦 **GORM** (ORM for Golang)
- **Observability**: 🐆 **Jaeger**, 🌐 **OpenTelemetry (Otel)**
- **Monitoring**: 📊 **Prometheus**
- **Containerization**: 🐋 **Docker**

## Technical Decisions & Trade-offs

**gRPC as the API surface for a CRUD app**
Protobuf contracts give the movie endpoints typed messages and efficient binary serialization, which is the main reason to pick gRPC over REST here. The cost is tooling friction: no browser access, no quick curl against JSON, and any external consumer needs a generated client or grpcurl. For an internal service-to-service demo, that friction is the point being demonstrated.

**Gin and GORM for speed of development**
Gin keeps the HTTP layer thin and GORM removes hand-written SQL from the CRUD paths, so the app comes together quickly. The trade-off is that the ORM hides the actual queries, which complicates tuning and can behave unexpectedly under load. At movie-catalog scale, convenience wins and the hidden SQL never becomes a real problem.

**A tracing stack heavier than the app itself**
OpenTelemetry feeds spans to Jaeger while Prometheus scrapes metrics, on a service with only a handful of endpoints. Honestly, the observability containers cost more resources than the application they watch. That is intentional: the project is a template for instrumenting a real service, where this overhead pays for itself the first time a request misbehaves.

**Docker for the whole observability pipeline**
Compose ties the app, collector, Jaeger, and Prometheus together so anyone can reproduce the full setup with one command. The cost is a stack of containers to keep running for a small service, plus image versions to pin. For a project that is about tooling, reproducibility across machines is worth that overhead.
