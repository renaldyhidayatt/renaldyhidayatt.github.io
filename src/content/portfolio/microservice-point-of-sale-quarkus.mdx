# Distributed Microservices — Point of Sale Platform (Java Quarkus)

A production-grade, highly resilient, and fully observable **microservices point of sale (POS) backend** built in **Java 21** on the **Quarkus** reactive framework (v3.31.3). Designed around domain-driven service boundaries following Clean Architecture and CQRS principles, each service runs as an **independent JVM process** with its own gRPC server, database migrations, and caching layer — true service-level isolation and independent deployability.

Each retail and identity domain — Users, Roles, Cashiers, Merchants, Categories, Products, Orders, Order Items, Transactions — lives in its own self-contained Maven module as a **standalone microservice**. They communicate synchronously over high-performance **gRPC** and asynchronously through **Apache Kafka**, exposing a unified reactive entry point via a **REST API Gateway** powered by Quarkus RESTEasy Reactive.

Beyond the business domains the platform ships a **ClickHouse analytics layer** (stats-reader, stats-writer, stats-backfill), a **transactional outbox** for lossless event publishing, and a full observability suite (Prometheus, Grafana, Loki, Jaeger, OpenTelemetry) with Kubernetes manifests delivered through **ArgoCD GitOps**.

## Architecture Overview

Every business service is an independent JVM process with its own gRPC boundary, connection pool, and cache. A **Quarkus REST API Gateway** is the single edge router, translating client REST calls into fast gRPC calls through Quarkus gRPC clients.

### Core Architecture Principles

- **Service-Level Isolation**: Every microservice runs as its own JVM with its own gRPC server, connection pool and Flyway migrations, and cache layer. No shared-memory coupling between services.
- **Clean Architecture & CQRS**: `Handler (gRPC) → Service (Command/Query) → Repository` keeps business logic clean and framework-agnostic.
- **Reactive Execution**: Quarkus reactive engine with Mutiny throughout, for high throughput at a minimal resource footprint.
- **Direct DB Connections**: Each service owns its own Agroal pool against PostgreSQL, with per-service `max-size` and `acquisition-timeout` — no external connection proxy.
- **Event-Driven Resilience**: Kafka decouples side effects through the transactional outbox, so emails and analytics never block a business write.
- **CQRS & OLAP Split**: OLTP writes stay in PostgreSQL; heavy aggregations are served from ClickHouse populated asynchronously from Kafka.
- **OTel Telemetry**: OpenTelemetry middleware injects trace IDs across gRPC boundaries, so a request can be followed from the REST edge down to the database.

## Data & Event Flow

### Synchronous Flow (REST proxy, gRPC, cache read-through)

Client requests enter through NGINX, are validated by the gateway, forwarded over gRPC to the owning domain service, checked against Redis, and only fall through to the database on a cache miss.

```mermaid
sequenceDiagram
    autonumber
    participant C as Client
    participant GW as API Gateway<br/>(Quarkus REST)
    participant SVC as Domain Service<br/>(gRPC Server)
    participant R as Redis
    participant DB as PostgreSQL

    C->>GW: REST HTTP Request
    GW->>GW: JWT / API Key Validation
    GW->>SVC: gRPC Call (Protobuf)
    SVC->>R: Check Cache
    alt Cache Hit
        R-->>SVC: Cached Response
    else Cache Miss
        SVC->>DB: Reactive SQL (Agroal Pool)
        DB-->>SVC: Result Set
        SVC->>R: Populate Cache
    end
    SVC-->>GW: gRPC Response
    GW-->>C: REST HTTP Response (JSON)
```

### Asynchronous Flow (outbox → Kafka → consumers)

State-changing operations write an outbox row in the same transaction as the business write. `OutboxPublisher` relays pending records to Kafka, where the email worker and analytics consumers pick them up independently — consumers can lag or restart without blocking a business operation.

```mermaid
sequenceDiagram
    autonumber
    participant SVC as Domain Service
    participant OB as Outbox Table (status=PENDING)
    participant OP as OutboxPublisher
    participant K as Kafka
    participant EM as Email Service
    participant SW as Stats Writer
    participant CH as ClickHouse

    SVC->>OB: Write event (same transaction)
    OP->>OB: Poll pending rows
    OP->>K: Publish topic payload
    K-->>EM: Deliver (email-service-topic-*)
    K-->>SW: Deliver batch (stats.*.event)
    SW->>SW: Deduplicate + batch
    SW->>CH: FlushScheduler batch INSERT
```

## ClickHouse Analytics Layer

Heavy aggregations — revenue, volume, and per-domain breakdowns — never touch the transactional store. They are served from ClickHouse, populated in near real time.

```mermaid

    classDef olap fill:#1e293b,stroke:#a855f7,color:#f3e8ff,stroke-width:1.5px

    DB[("PostgreSQL OLTP")]:::pg
    OB[("Outbox (PENDING)")]:::pg
    OP["OutboxPublisher"]:::olap
    K[("Kafka stats.*.event")]:::kafka
    SW["stats-writer<br/>Dedup + Batch"]:::olap
    CH[("ClickHouse")]:::pg
    SR["stats-reader<br/>gRPC :9015"]:::olap
    RC[("Redis Cache")]:::pg
    GW["API Gateway"]:::olap

    DB --> OB --> OP --> K
    K --> SW --> CH
    GW --> SR --> CH
    SR --> RC
    SR --> GW
```

- **stats-writer** consumes domain event topics, deduplicates by `event_id`, batches, and flushes to ClickHouse via `ClickHouseBatchWriter`.
- **stats-reader** exposes gRPC analytics queries, caching hot aggregates in Redis.
- **stats-backfill** is a one-shot loader that replays historical PostgreSQL rows through outbox → Kafka → ClickHouse. Because it goes through the outbox it is **idempotent for free** — a re-run hits the unique `backfill:<domain>:<id>` constraint and inserts nothing.

## Technical Decisions & Trade-offs

### Technical Decisions & Trade-offs

**Microservices for a retail workload that fits on one box**
A POS chain has uneven scale: checkout volume is spiky while merchandising is quiet. Independent services let the order path scale on its own and let each team ship without coordinating a monolith release. The cost is operational — a shop-floor deployment that used to be one artifact is now a fleet, and every new service adds manifests, probes, and dashboards.

**Synchronous gRPC for price lookup and checkout**
A cashier cannot wait for an eventually consistent price, so the order service resolves product prices synchronously. The cost is a hard dependency on the product service during checkout — mitigated by Redis caching price lookups, which introduces the classic staleness question when a price changes mid-shift.

**Transactional outbox for receipts and audit**
A receipt or ledger row that exists without its event — or the reverse — is the classic retail inconsistency. Writing the outbox record inside the same transaction as the order removes it. The cost is an extra collection/table and a relay loop whose lag must be alerted on, which for a single-shop deployment is real operational weight.

**ClickHouse for cashier and sales reporting**
Daily and monthly sales volumes, cashier performance, and sold-out product tracking are aggregations that must not compete with checkout for database capacity. ClickHouse handles them. The trade-off is that closing a shift and immediately seeing that shift's totals is inconsistent — the reporting must be explicit about its lag.

## Getting Started

### Prerequisites

- [Git](https://git-scm.com/)
- [JDK 21](https://adoptium.net/)
- [Maven](https://maven.apache.org/)
- [Docker](https://www.docker.com/) & [Docker Compose](https://docs.docker.com/compose/)
- [Hurl](https://hurl.dev/) (for the validation suites)

### 1. Clone the Workspace

```sh
git clone https://github.com/MamangRust/microservice-pointofsale-quarkus.git
cd microservice-pointofsale-quarkus
```

### 2. Prepare Environment Configurations

```sh
cp .env.example .env
cp deployments/local/docker.env.example deployments/local/docker.env
cp deployments/local/host.env.example deployments/local/host.env
```

### 3. Build the Maven Project

```sh
mvn -B clean install -DskipTests
```

### 4. Start Infrastructure & Launch Microservices

```sh
# Start infrastructure containers (PostgreSQL, Redis, Kafka, ClickHouse, observability)
docker-compose -f deployments/local/docker-compose.yml up -d

# Launch all Java microservices on the host
deployments/local/run-host-java.sh start
```

### 5. Run the Validation Suites

```sh
deployments/local/tests/checks/smoke.sh
BASE_URL=http://localhost:5000 deployments/local/tests/run-e2e.sh
BASE_URL=http://localhost:5000 deployments/local/tests/run-stats.sh
```

To stop everything:

```sh
deployments/local/run-host-java.sh stop
docker-compose -f deployments/local/docker-compose.yml down -v
```
