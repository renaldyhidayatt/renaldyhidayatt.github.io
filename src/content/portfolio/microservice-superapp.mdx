# Microservice Superapp — Unified Vert.x Ecosystem

Four business platforms — **E-Commerce (20 modules)**, **Point of Sale (11 modules)**, **Payment Gateway (11 modules)**, and a Quarkus-based **ERP (17 modules)** — connected through one Unified API Gateway, one Kafka KRaft event bus, and one gRPC bridge into the ERP. **63+ Maven modules**, **2,251+ green unit tests** across all four platforms, deployed on Kubernetes with ArgoCD.

The design goal: keep every platform independently modular (domain-driven Maven modules with their own gRPC boundaries), while exposing a single hardened edge and a single asynchronous integration fabric.

---

## Key Features

| Feature | Description |
|---------|-------------|
| **Unified API Gateway** | Single entry point (`:8080`) routing `/api/ecommerce/*`, `/api/pos/*`, `/api/payment/*`, `/api/erp/*` with JWT validation, RBAC claims check, and 500 req/min/IP rate limiting |
| **Event-Driven Core** | Apache Kafka (KRaft mode, no ZooKeeper): `user.registered`, `order.payment.requested`, `payment.completed`, `inventory.stock.synced`, `order.status.updated`, `accounting.journal.entry` |
| **Dual Auth Paths** | Registration & email verification via Identity Service (`:8085`, bcrypt + verification codes); login & token issuance via Keycloak OIDC (realm `superapp`, RS256); gateway validates JWT against cached JWKS |
| **ERP Bridge** | Quarkus bridge (`:8084`) translating REST/gateway traffic into gRPC (`:9000`) plus Kafka consumers that turn domain events into ERP journal entries |
| **Money Movement** | Idempotent card/saldo/topup/transfer/withdraw flows with outbox-pattern events (`payment_event_outbox`) |
| **eBPF Security Sidecars** | `ebpf-observability` DaemonSet (kprobe CO-RE telemetry, 9 Sigma rules) and `ebpf-firewall` sidecar (XDP L3/L4 drop engine + iptables/nftables sync) |
| **Full Observability** | OpenTelemetry → Prometheus, Grafana, Loki, Jaeger across every service |

### Request Lifecycle (happy path)

1. Client sends `POST /api/ecommerce/orders` with Bearer token.
2. Gateway checks rate limit, verifies RS256 signature/exp/issuer/audience via Keycloak JWKS (cached, retry with exponential backoff), checks RBAC claims.
3. Request proxies to the E-Commerce gateway, which calls the OrderService over gRPC.
4. Service writes to PostgreSQL through PgBouncer, publishes `order.created` to Kafka.
5. ERP Bridge consumes the event and creates a journal entry (Debit: Cash / Credit: Revenue).
6. Response returns `201 Created {orderId}` end-to-end.

## Data Architecture

- **PostgreSQL 17** with per-domain databases, always accessed through **PgBouncer** pooling.
- **Three isolated Flyway zones** so module migrations never collide: shared history on `PAYMENT_GATEWAY` (ecommerce + POS + payment), isolated identity history table, and a separate Quarkus-managed ERP database.
- **Redis 7 cluster** for token blacklists, sessions, and read-through caching.
- Outbox pattern for payment events guarantees at-least-once delivery of financial events without dual writes.

Core money-movement entities (`users`, `cards`, `saldos`, `transactions` with `idempotency_key`, `saldo_operations` ledger, card credit/auth/billing/rewards tables) are modeled as an explicit ERD in the project README.

## Technical Decisions & Trade-offs

**Domain-driven decomposition across four platforms**
E-Commerce, POS, Payment Gateway, and ERP are split into 63+ Maven modules, each domain owning its own gRPC boundaries, so every platform stays independently buildable, testable, and deployable. The cost is real: module wiring, contract versioning, and cross-module refactors take longer than editing one codebase, and the build graph is harder to hold in your head. At four platforms' worth of surface area, that discipline is what keeps the system navigable.

**Kafka as the integration fabric**
Cross-platform flows such as order payment requests, payment completion, and ERP journal entries travel as events on one Kafka KRaft bus, so platforms stay decoupled and a slow consumer never blocks a checkout. The price is eventual consistency everywhere: consumers must be idempotent, and debugging means correlating events instead of reading one stack trace. For money movement across platform boundaries, a durable log beats tight synchronous coupling.

**Dual auth paths: Identity Service plus Keycloak**
Registration and email verification run through a dedicated Identity Service with bcrypt and verification codes, while token issuance is delegated to Keycloak OIDC with RS256, verified at the gateway against cached JWKS. Running two auth components adds operational surface a Keycloak-only setup would not have. The payoff is full control over custom registration flows without hand-rolling token signing, realm management, or JWKS rotation.

**The ERP stays a monolith behind a bridge**
The 17-module Quarkus ERP is a single deployable, reached through a REST-to-gRPC bridge plus Kafka consumers that turn domain events into journal entries. Keeping the ERP's tightly related accounting logic in one process preserves transactions and simple evolution; the cost is that it scales and deploys as a unit. For a domain where modules share the same ledgers, that is the right default, and the bridge buys integration without forcing a premature microservice split.

**Outbox pattern for payment events**
Payment events are persisted to an outbox table in the same transaction as the state change before being published, guaranteeing at-least-once delivery without dual-write inconsistencies. The trade-off is extra schema, a relay to run, and consumers that must tolerate duplicates. Losing or duplicating a financial event costs more than all of that.

**Observability and eBPF sidecars from day one**
OpenTelemetry, Prometheus, Grafana, Loki, and Jaeger, plus eBPF DaemonSets for kprobe telemetry and an XDP drop engine, mean a lot of containers running before a single business request is served. The honest cost is cluster resource usage and a steeper local setup. Across 17+ pods on four platforms, debugging without traces, metrics, and per-service logs costs more the first time a payment disappears between the gateway and the ledger.
