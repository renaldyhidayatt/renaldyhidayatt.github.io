# 💳 Point of Sale (POS) gRPC Project

This project is a **backend implementation for a Point of Sale (POS) system** designed with a **structured monolithic** architecture. Although monolithic, the project is organized into clear modules so that each domain (users, merchants, inventory, and transactions, for example) remains easy to manage and can be extended further without losing order.

The main goal of this project is to provide a **solid, secure, and scalable foundation** for modern cashier applications used by many kinds of retail businesses. With its structured design, the system can handle day-to-day cashier needs ranging from user and inventory management to recording sales transactions, while staying easy to deploy in various environments.

Communication between client and server happens over a **REST API**, while internal communication between the API Gateway and the core service uses **gRPC** with **Protobuf**. This ensures the system has **low latency and high throughput**, so it stays responsive even when handling large numbers of transactions. Transaction data and entity management are stored securely in **PostgreSQL**, which is known to be stable and reliable for financial and operational needs.

### Scope and Key Features

* **🔐 User & Role Management**
  The system supports authentication and authorization with different access levels (admin, merchant owner, cashier). This ensures that only authorized parties can perform certain actions according to their responsibilities.

* **🏬 Merchant Management**
  Business owners can register a store/merchant, configure important information such as store name and API key, and set up their operational structure.

* **👨‍💼 Cashier Management**
  Merchants can add cashier accounts, grant access as needed, and monitor their cashiers' activity in real time.

* **📦 Inventory Management**
  Supports full CRUD for products and categories, covering stock details, price, description, and product category. With this system, stock is always up to date and can be controlled efficiently.

* **💳 Transaction Processing**
  The system provides a complete flow for creating orders, adding items to the cart, calculating the payment total, and recording transactions permanently in the database.

* **⚡ Internal gRPC Communication**
  The API Gateway communicates with the core server over gRPC, which delivers high performance and makes future scaling easier if the system is later split into microservices.

* **📖 Automatic API Documentation**
  The REST API is automatically documented with Swagger (**Swago**), making it easier for developers and integration teams to understand and test the available endpoints.

* **🐳 Containerization with Docker**
  The system is ready to run in an isolated environment with Docker & Docker Compose, making setup fast, consistent, and easy to deploy across platforms.

## 🧰 Tech Stack

- 🐹 **Go (Golang)** — Implementation language.
- 🌐 **Echo** — Minimalist web framework for building REST APIs.
- 🪵 **Zap Logger** — Structured logging for high-performance applications.
- 📦 **SQLC** — Generates type-safe Go code from SQL queries.
- 🚀 **gRPC** — High-performance RPC for internal service communication.
- 🧳 **Goose** — Migration tool for managing database schema changes.
- 🐳 **Docker** — Containerization platform for a consistent development environment.
- 📄 **Swago** — Generates Swagger 2.0 documentation for Echo routes.
- 🔗 **Docker Compose** — Manages multi-container Docker applications.

## Technical Decisions & Trade-offs

**REST at the edge, gRPC inside**
The Echo REST gateway faces clients and translates HTTP requests into gRPC calls to the core server. This keeps browsers and Swagger integrators happy on the outside while internal calls stay typed, binary, and low-latency. The cost is two API layers to keep in sync and translation code that does nothing but forward — a fair price for getting both worlds.

**SQLC instead of a full ORM**
SQLC generates typed Go straight from hand-written SQL, so a bad query or a mismatched column fails at compile time. The trade-off is that every query is written and maintained by hand, with none of the dynamic query building an ORM gives you. For a POS domain where the queries are few and stability matters more than flexibility, explicit SQL is the better deal.

**A monolith with service-shaped seams**
Everything deploys as one server and one REST client, but modules for users, merchants, inventory, and transactions stay separated behind the gRPC boundary. Scaling is all-or-nothing, and an outage takes down every domain at once. The payoff is operational simplicity and a clean path to split into microservices later, which suits retail POS traffic.

**PostgreSQL for stock and sales integrity**
Inventory decrements and sales records must commit together or the till sells stock it no longer has. PostgreSQL's ACID guarantees cover that, and Goose keeps schema changes versioned. The cost is a fixed relational schema and migration ceremony on every model change — acceptable for financial and operational data.

**Auto-generated Swagger for the REST surface**
Swago turns Echo routes into Swagger 2.0 documentation, so integrators can discover and test endpoints without reading code. The limitation: it documents only the REST layer, while the gRPC contracts still require reading the proto files. That asymmetry is tolerable because external consumers only ever touch the gateway.

**Docker Compose as the one-command environment**
One make target builds the server, client, and migrate images, boots PostgreSQL, and applies migrations in order. The trade-off is that the whole stack must come up together locally, and image builds slow the edit-run loop. For a project with a migration step and two processes, that reproducibility is worth it.

## 🚀 How to Run the Project

Follow these steps to run the project in your local environment.

### 1. Prerequisites

- [Go](https://golang.org/doc/install) (versi 1.20+)
- [Docker](https://www.docker.com/get-started) and [Docker Compose](https://docs.docker.com/compose/install/)
- [Make](https://www.gnu.org/software/make/)
- [Git](https://git-scm.com/downloads)

### 2. Clone the Repository

```bash
git clone https://github.com/your-username/point-of-sale-grpc.git
cd point-of-sale-grpc
```

### 3. Environment Configuration

Copy `.env.example` to `.env` for local configuration and `docker.env.example` to `docker.env` for Docker configuration.

```bash
cp .env.example .env
cp docker.env.example docker.env
```

Adjust the variables in the `.env` and `docker.env` files to match your local setup (for example, database credentials).

### 4. Running with Docker (Recommended)

This is the easiest way to get started.

```bash
make docker-up
```

This command will:
1. Build Docker images for `server`, `client`, and `migrate`.
2. Start the PostgreSQL database.
3. Run database migrations automatically.
4. Start the gRPC `server` and the REST API `client`.

To stop all services, run:
```bash
make docker-down
```

### 5. Running Locally

If you do not want to use Docker, follow these steps:

**a. Start the Database**
Make sure you have a PostgreSQL instance running locally and configure the connection in the `.env` file.

**b. Run the Database Migrations**
```bash
make migrate
```

**c. Generate Protobuf Code**
If you change a `.proto` file, run this command:
```bash
make generate-proto
```

**d. Start the gRPC Server**
```bash
make run-server
```
The server will run on the port specified in `.env` (default: `50051`).

**e. Start the Client (REST API)**
Open a new terminal and run:
```bash
make run-client
```
The REST API client will run on the port specified in `.env` (default: `5000`).
