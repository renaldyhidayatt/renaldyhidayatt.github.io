# Platform Labs — Sovereign Mini-Cloud Control Plane (Go)

A **15-domain platform lab** that mirrors a modern infrastructure control plane — security, telemetry, delivery, and intelligence — written entirely in **Go**. Each domain is a **separate Go module**, and all of them are connected through a **gRPC contract defined in one place**, then tested end-to-end against that same contract.

The goal is not to replace Kubernetes or Kafka. It is to **understand the control plane from the inside**: how reconcile loops, detection, enforcement, and actuation actually work when you have to build them yourself.

---

## Position in the PIERO LOKA ecosystem

Platform Labs is the Go embodiment of **PIERO LOKA**, a high-performance eBPF-based security and FinOps monitoring platform, rendered here anew as a 15-domain mini-cloud control plane.

PIERO LOKA uses a **Core Dispatcher** pattern: more than 28 kernel hooks are consolidated into 6 high-performance kernel entry points with zero-copy ring buffers and internal event correlation, cutting kernel overhead and context switches by 60–75% with total system overhead under 1.5%. The same discipline carries into this Go version — kernel signals are the source of truth, and a capability is stated exactly as it behaves.

## Capability tracking, without the labels

A recurring theme in this lab is that a claim should be checkable. Instead of a boolean "done / not done", every domain reports structured capability data: what kind of implementation backs a feature, how it executes (in the OS, in the kernel, in a simulator, or as a model), and what it requires to run — a capability such as `CAP_BPF` or a device such as `/dev/kvm`. An aggregate call summarises the coverage per domain in one round trip, and a boot-time sweep produces the lab summary.

The important part is that **tests enforce the report**. A capability that cannot run must carry a stated reason; a value that is not part of the official vocabulary fails the suite; and an architecture test fails if a domain reaches into another domain's generated types. When a claim and the host disagree, the test wins — not the README.


Concretely: on a host without `CAP_BPF`, KernelForge still boots — the kernel loader fails as-is, modules run under the simulator, and the capability report says exactly that. There is no "hide the simulator" switch. Without `/dev/kvm`, a VM reports software acceleration rather than claiming it is ready; with KVM it reports hardware acceleration.

## Security response chain

This is the core flow of the lab: a finding does not stop at an alert — it flows through until enforcement happens, and every step has a clear owner.

```mermaid
sequenceDiagram
    autonumber
    participant EDR as Endpoint Sensor
    participant DET as Detection Platform
    participant KF as KernelForge (eBPF)
    participant NET as Network
    participant PDP as Security PDP
    participant OPS as Operations
    participant HITL as Human-in-the-loop gate

    EDR->>DET: event / finding
    DET->>KF: correlation + kernel telemetry
    KF-->>DET: typed BPF event stream
    DET->>OPS: finding becomes an incident
    OPS->>PDP: request a response decision
    PDP-->>OPS: allow / deny (default-deny)
    alt high-risk
        OPS->>HITL: escalation to the operator console
        HITL-->>OPS: approve / reject
    end
    OPS->>NET: BlockIP
    NET->>KF: UpdateMap (network_block_list)
    KF-->>NET: installed or failed, reported as-is
```

Semantic ownership is strictly guarded: Network owns `BlockIP`, KernelForge owns `UpdateMap`, Security owns the policy decision. No domain touches another domain's maps directly — everything goes through contracts.

What is exported goes beyond health: the **Go runtime** (GC pause histogram from `runtime/metrics`, heap, goroutines), **per-RPC** gRPC metrics carrying a `domain` attribute, and **per-domain business instruments**. The exporter only activates when an external collector endpoint is configured. Without it, spans are no-ops and metrics are not emitted at all, which the docs state plainly rather than implying the numbers exist.

## Real actuation, not just a reconcile diagram

What sets this lab apart from a renamed CRD: several paths genuinely change system state.

| Path | What actually happens |
| :--- | :--- |
| `compute.pod` | A process with new namespaces (PID/UTS/IPC/Mount/User) under **cgroup v2** `memory.max`, `cpu.max`, and `pids.max`; `oom_killed` read from `memory.events` |
| `storage.volume` | **Sparse** volumes and **COW** snapshots with refcounting; `physical_size` reports actual physical bytes |
| rtnetlink | Create and delete bridges and veths, bring links up, move netns via `NETLINK_ROUTE` sockets using `x/sys/unix`, no third-party libraries |
| eBPF | Load and attach to the kernel when the capability is available; otherwise a simulator that is never disguised as the kernel |
| Right-sizing | A real cgroup v2 sampler → recommendation (percentile × headroom, clamped) → human-gated desired state → live cgroup resize with a kill switch |

## Technical decisions & trade-offs

**One repo, 15 separate modules — not one big module.** Each domain has its own `go.mod`, which curbs the pull toward cross-imports: if Detection wants a KernelForge type it has to reach into the generated package, and a test fails. The cost is messier wiring through `replace` directives, but the architectural boundaries become real instead of aspirational.

**A shared `grpcrun` substrate.** Health, TLS, breaker, retry, OTel, and cert renewal live in one place, so consistency across 15 domains comes for free. The risk is that a bug there spreads everywhere at once; the mitigation is that the substrate itself is tested against an in-process OTLP receiver.

**Typed contracts, no `map<string,string>`.** Payloads are protobuf messages with typed fields, so contract errors surface at compile time instead of at runtime. The cost is more `.proto` files and regeneration steps, but magic fields holding undocumented strings disappear.

**Capability as data, not intent.** Because every feature must declare its requirements from the start, capability cannot be deferred with "we'll report it later". The trade-off is one extra level of boilerplate per feature — a fair price for claims that can be verified.

**One process for everything during development.** `labnet` boots 15 domains in one process without Docker, Kubernetes, or an external database, which speeds up iteration dramatically — and it is consciously not a production topology, which the docs say outright.

## What works, what is simplified, what is missing

An honest map rather than a maximal one.

**Genuinely running on a real host:** pods with their own namespaces and cgroup v2, sparse volumes and COW snapshots, an object store with SHA-256 scrubbing, network packet decoding, the full detection pipeline, the Sigma rule subset, the host endpoint sensor, the mTLS domain CA, eBPF modules from loader to simulator, MCP tool execution, complete OTel metrics, and the cluster watcher via client-go.

**Deliberately simplified:** network reconcile (its netlink path is not fully wired), the deploy step inside workflows (still a no-op), the Kubernetes catalog in PlatformForge, and chaos targets.

**Not there yet because the infrastructure is not available:** a real Kubernetes cluster, registry pushing, a production-grade OTLP collector, outgoing Alertmanager, the live-root gate for cgroup resize, and admission webhooks.

Every per-feature status is announced through the capability API, and the tests keep those announcements from drifting from reality. If a claim and reality differ, the test wins — not the README.

## Running

All tooling lives in the `Makefile` inside `GrpcConnect/`:

```bash
cd GrpcConnect

make gen            # generate proto -> gen/
make test           # unit test all packages (go test -race ./...)
make test-e2e       # 18 cross-domain e2e scenario files (bufconn, -race)
make count-rpc      # count RPCs per domain from the .proto files
make run-lab        # boot 15 domains + bridges (single process, dev)

LABNET_MTLS=1 make run-lab   # same, with the mTLS domain CA enabled
make run-hardware            # Hardware :5001 (standalone)
make run-compute             # Compute :5002
# ... one target per domain, up through make run-cyber (Cyber :5013)
make run                     # KernelForge :5014 (cmd/bpfgrpc)
```

Environment variables that change behaviour:

| Variable | Effect |
| :--- | :--- |
| `LABNET_MTLS=1` | All labnet clients load a client certificate from their domain CA |
| `OTLP_ENDPOINT=host:port` | Enable OTLP spans and metrics to the collector; without it, nothing is exported |
| `NETWORK_IPAM_DIR=/path` | Persistent IPAM via atomic JSON snapshot; otherwise in-memory |
| `DETECTION_SIGMA_DIR=/path` | Load Sigma rules; failed files are skipped and reported |
| `PIEROLOKA_IFACE` / `PIEROLOKA_CGROUP2` / `PIEROLOKA_UPROBE` | eBPF attach targets (XDP/TC, cgroup_skb, SSL uprobe) |

## Closing

Platform Labs is an exercise in building a control plane from the bottom up with one hard discipline: never claim more than what actually runs. Every capability is reported as data and enforced by tests, every metric on the dashboards has a declaration in code, and every gap is written out plainly instead of hidden.

The result is not a generic orchestrator but something more useful for learning: a system where the architecture diagram, the real capabilities, and the runtime status agree with each other — and when they do not, the tests catch it.
