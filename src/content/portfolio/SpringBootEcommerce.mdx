# Spring Boot E-Commerce API

**High-Performance Backend API for a Full-Featured E-Commerce Platform**

The `Spring Boot E-Commerce API` is a high-performance backend system designed to support a complete digital commerce ecosystem. Built with **Java 21** and **Spring Boot**, it provides a comprehensive set of capabilities including JWT-based authentication, user and role management, product and category management, shopping cart operations, order processing, product reviews, merchant management, and shipping address handling.

---

## Core Features

### 1. Authentication & Security

* **JWT Authentication:** Secure user registration and login using JSON Web Tokens.
* **Role-Based Access Control (RBAC):** Granular permission model separating access for administrators, merchants, and customers.

### 2. Product & Category Management

* **Product CRUD Operations:** Full lifecycle management for product entities, including creation, updates, retrieval, and deletion.
* **Category Management:** Structured product categorization to improve searchability and navigation across the platform.

### 3. Shopping Cart & Order Management

* **Shopping Cart System:** Real-time cart operations including add, update quantity, remove items, and cart retrieval.
* **Order Processing:** End-to-end order lifecycle management with total price calculation and transactional consistency.

### 4. Merchant & Business Features

* **Merchant Onboarding:** Enables merchants to register and operate within the platform.
* **Merchant Profiles:** Supports detailed merchant identity including branding and business metadata.

### 5. Reviews & Shipping

* **Product Reviews:** Users can submit ratings, comments, and media attachments for purchased products.
* **Shipping Address Management:** Structured address handling to support checkout and delivery workflows.

---

## Technology Stack

* **Programming Language:** Java 21
* **Framework:** Spring Boot 3.x
* **Security:** Spring Security with JWT
* **ORM / Data Layer:** Spring Data JPA (Hibernate)
* **Database:** PostgreSQL
* **Build Tool:** Maven
* **API Documentation:** Springdoc OpenAPI (Swagger UI)

## Technical Decisions & Trade-offs

**Spring Boot 3.x and Java 21 vs lighter stacks**
Spring Boot buys a mature, batteries-included ecosystem: Spring Security handling JWT, Springdoc generating Swagger UI, and a consistent configuration model with almost no glue code. The cost is real — JVM memory footprint, startup time, and plenty of ceremonial code (DTOs, mappers, layer interfaces) that a Go or Node service would not need. At the scale of a portfolio API, developer velocity and type safety outweigh the resource overhead.

**Spring Data JPA (Hibernate) vs raw SQL**
Repository interfaces and entity relationships keep a 20-plus-table relational model manageable, and the persistence code stays database-agnostic. The price is a leaky abstraction: lazy-loading pitfalls, N+1 query risk on relationships like order items and reviews, and little visibility into the SQL Hibernate actually emits. For CRUD-heavy commerce flows that is an acceptable trade; hand-tuned SQL only pays off under heavy read load.

**PostgreSQL vs a document store**
An e-commerce schema spanning users, merchants, products, carts, orders, and transactions is fundamentally relational — an order must atomically bind a user, its order items, and a shipping address, and referential integrity should be enforced by the database rather than application code. The trade-off is schema rigidity: every new attribute means a migration, and horizontal scaling is harder than with documents. Consistency matters more here than flexibility.

**JWT with refresh tokens vs server sessions**
Stateless JWTs keep the API horizontally scalable with no session store, and the dedicated refresh-token table allows token rotation and per-user revocation paths. The cost is that security changes such as logout-everywhere or role downgrades take effect only as fast as token expiry, and client-side token handling is more complex than a cookie session. For a stateless public API this remains the standard, defensible choice.

**Single deployable vs microservices**
Auth, catalog, cart, orders, reviews, and merchant management all live in one process over one database, which keeps transactional boundaries trivial and deployment a single jar. What is given up is independent scaling and fault isolation — a burst of review writes pressures the same pool as checkout. Splitting would only pay off at team and traffic scales this project does not operate at.

**Stock integrity on checkout (the core domain risk)**
Products carry a countInStock column that order fulfillment must decrement. The honest risk is the race: two concurrent checkouts reading the same stock can oversell unless the decrement runs inside the same transaction as order creation, ideally as a conditional update that only applies when stock is sufficient rather than a read-then-write. Application-level checks alone are the cheapest implementation and the easiest one to break under load.

## Getting Started

### Prerequisites

* Java Development Kit (JDK) 21 or higher
* Apache Maven
* PostgreSQL (running locally or remotely)

### Installation Steps

**1. Clone the repository**

```bash
git clone https://github.com/MamangRust/example-ecommerce-springboot-new
cd example-ecommerce-springboot-new
```

**2. Configure the database**
Update `src/main/resources/application.properties`:

```properties
spring.datasource.url=jdbc:postgresql://localhost:5432/ecommerce_db
spring.datasource.username=postgres
spring.datasource.password=postgres
spring.jpa.hibernate.ddl-auto=update
```

**3. Run the application**

```bash
./mvnw spring-boot:run
```

**4. Access the API**

* Base URL: `http://localhost:8080`
* Swagger UI: `http://localhost:8080/swagger-ui.html`
