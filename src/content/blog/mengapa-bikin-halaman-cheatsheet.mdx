# Why I Built a Cheatsheet Page (and Why Not a Blog)

There is one problem that never gets solved if you only have a blog: **my intent is to write
explanations, but what I need is often just a single line**.

A real example: I was debugging a deadlock in a payment service and needed to remember how to check
PostgreSQL locks. My blog post about *transactional outbox* was right there — but it was 3,000 words, 8
headings, and there was no quick way to get to `pg_locks`. What I needed at that moment was: one
query, one output, and the context of when that query is used.

So I ended up with three different needs that collide with each other when forced into a single
page:

| | Blog | Portfolio | Cheatsheet |
| :--- | :--- | :--- | :--- |
| Form | essays, stories that explain *why* | case studies + the cost of decisions | a quick dictionary: *when & how* |
| Marker | date written | project date | **locked version** (`Spring Boot 3.5.6`, `PostgreSQL 17`) |
| Content | trade-offs, history, failures | architecture + consequences | **lookup tables + copy-ready snippets + pitfalls** |
| Reading direction | linear, top to bottom | linear, top to bottom | **non-linear, straight to the table** |
| Lifespan | remains valid as a historical record | frozen per project version | **expires when the major version changes** |

So I built a new section: [Cheatsheet](/cheatsheet).

## The rules I hold myself to

So this doesn't turn into a second blog, there are four rules I enforce.

**1. Versions are pinned, no "latest".**
Every sheet opens with the exact version used in my repo at that time. If the
library version has moved past one major, the sheet is marked outdated — I don't quietly rewrite it
and consider it up to date. A cheatsheet that is quietly wrong is more dangerous than not having one.

**2. No narrative.**
If a paragraph needs more than two sentences of context, that's not a cheatsheet's job
— that's a blog article. A cheatsheet answers a question, a blog answers the question *plus* the story
behind it.

**3. Every pitfall must have a symptom.**
The "Pitfalls" table in each sheet must not stop at "this is wrong". The format is always:

> Pitfall → visible symptom → solution.

"Pitfall: `@Transactional` doesn't work on self-invocation" without a symptom = a personal
note, not a reference.

**4. Snippets must be run.**
The rule of thumb: if I have never run `mvn test` or `zig test` on it, the snippet doesn't
go into the sheet. The difference from a blog: on a blog I'm allowed to be wrong and correct it in the next
article (that's part of the process). In a cheatsheet, mistakes are immediately used by other people.

## Why backend, not just languages

My Zig cheat sheet was the starting point, but it's actually the contents that I open most often:
not the syntax of a language, but **patterns that repeat in the backend**:

- One transaction pattern: `BEGIN → change data → write outbox → COMMIT → relay`.
- One idempotency pattern: a unique constraint in the DB, not a lock in memory.
- One observability pattern: metrics for aggregates, logs for details, traces for flows.

Those patterns show up in Java, Go, and MongoDB projects alike — and that's what makes
me need a **backend** cheatsheet, not a cheatsheet per language.

## What's coming next

six backend sheets already exist (Java/Spring Boot, gRPC/Protobuf, Kafka, PostgreSQL,
Docker/Kubernetes, Observability) plus one language sheet (Zig). Still on the list:
Redis, MongoDB, ClickHouse, Go, and one "daily Linux & CLI" sheet for the things most
often used while debugging.

If each project later has a **"pitfalls I ran into"** section, these sheets are what
will hold them — and the blog articles are enough to discuss *why* I chose that path.
