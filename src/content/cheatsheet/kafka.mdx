## Architecture & KRaft

```text
producer ──▶ [ broker 0 (leader p1,p2) ] ──▶ [ broker 1 (follower) ] ──▶ consumer
             [ broker 1 (leader p0)   ]        [ broker 2 (follower) ]
             [ controller quorum: broker 0,1,2 ]   <- KRaft, without ZooKeeper
```

| Concept | Meaning |
| :--- | :--- |
| **Broker** | Kafka node; stores partitions |
| **Controller quorum** | Raft quorum (3 or 5 nodes) for metadata — replaces ZooKeeper |
| **Leader / follower** | one leader per partition; followers replicate |
| **ISR** | in-sync replicas — followers that fall too far behind are removed from the ISR |
| **min.insync.replicas=2** | `acks=all` + ISR < 2 → producer **fails** (correct, don't change it) |
| **Consumer offset** | stored in the internal topic `__consumer_offsets` |
| **Epoch / leader election** | KRaft elects a new leader within seconds |

```properties
# server.properties (KRaft, combined broker + controller, 3 nodes)
process.roles=broker,controller
node.id=1
controller.quorum.voters=1@k1:9093,2@k2:9093,3@k3:9093
listeners=PLAINTEXT://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093
advertised.listeners=PLAINTEXT://broker1.example:9092
inter.broker.listener.name=PLAINTEXT
controller.listener.names=CONTROLLER
log.dirs=/var/lib/kafka/data
num.partitions=6
default.replication.factor=2
min.insync.replicas=2
log.retention.hours=168
log.segment.bytes=1073741824
compression.type=producer
```

```bash
# format KRaft storage (once per node) & start
kafka-storage.sh random-uuid
kafka-storage.sh format -t <cluster-id> -c /etc/kafka/server.properties
kafka-server-start.sh /etc/kafka/server.properties

# cluster metadata (replaces zkCli)
kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status
kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --replication
```

> **Pitfall:** in KRaft, `controller.quorum.voters` must be identical on **all** nodes. One node
> with a different voter list = the quorum never forms, the cluster can't hold an election.

## Topics, partitions, retention, compaction

```properties
# topic-level
retention.ms=604800000          # 7 days
retention.bytes=-1              # unlimited per partition (watch the disk)
cleanup.policy=delete|compact|compact,delete
segment.bytes=1073741824        # 1 GiB per segment - deletion granularity limit
segment.ms=86400000
min.insync.replicas=2
max.message.bytes=1048576
compression.type=producer
```

| Setting | Effect |
| :--- | :--- |
| `acks=all` | wait for all ISR replicas to acknowledge — no data loss as long as ISR ≥ 2 |
| `acks=1` | leader only — can be lost when the leader dies |
| `acks=0` | fire-and-forget — **don't** use for business data |
| `retention.ms` / `retention.bytes` | delete by age / size (whichever is hit first) |
| `cleanup.policy=delete` | delete old segments |
| `cleanup.policy=compact` | keep the **last value per key** (state, changelog) |
| `compact,delete` | compaction + time limit (tombstones still get deleted) |
| `min.cleanable.dirty.ratio` | how often compaction runs |
| `delete.retention.ms` | how long tombstones (`null` value) are kept |
| `segment.bytes` | smaller = more granular deletion, more files |

**Partitions = units of parallelism.** Throughput grows linearly with the partition count, but there is a cost:

| Need | Partitions | Trade-off |
| :--- | :--- | :--- |
| High throughput, no ordering | 12–24 | maximum consumers, ordering lost |
| Ordering per order | 6 + `orderId` key | 6 parallel consumers, ordered per key |
| Global ordering | 1 | 1 consumer, limited throughput |
| Events per merchant | 6 + `merchantId` key | ordering per merchant preserved |

| Important limit | Number |
| :--- | :--- |
| Partitions **increase** | allowed (`--alter --partitions`) |
| Partitions **decrease** | **not possible** — create a new topic + migrate |
| Recommended partitions per cluster | < 10,000 total for stable metadata latency |
| Replication factor | 3 in production (2 is homelab only) |
| `min.insync.replicas` | 2 (with RF=3 → tolerates 1 node down) |

> **Pitfall:** increasing the partition count **changes hash(key) → partition**. Events for the same key
> can move to another partition after the increase, so **per-key ordering breaks**.

## Producer (config, idempotence, batching, errors)

```java
Properties p = new Properties();
p.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
p.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
p.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);

// durability + no duplicates from retries
p.put(ProducerConfig.ACKS_CONFIG, "all");
p.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);      // default true since 3.0
p.put(ProducerConfig.RETRIES_CONFIG, Integer.MAX_VALUE);
p.put(ProducerConfig.MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION, 5);
p.put(ProducerConfig.DELIVERY_TIMEOUT_MS_CONFIG, 120_000);
p.put(ProducerConfig.REQUEST_TIMEOUT_MS_CONFIG, 30_000);

// throughput
p.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "lz4");       // zstd saves more CPU/disk
p.put(ProducerConfig.LINGER_MS_CONFIG, 5);
p.put(ProducerConfig.BATCH_SIZE_CONFIG, 32 * 1024);
p.put(ProducerConfig.BUFFER_MEMORY_CONFIG, 64L * 1024 * 1024);

KafkaProducer<String, String> producer = new KafkaProducer<>(p);
```

```java
// synchronous send (needs error handling & ordering) — slow
RecordMetadata md = producer.send(new ProducerRecord<>(
        "order.payment.requested", orderId, json)).get(5, TimeUnit.SECONDS);
log.info("partition={} offset={}", md.partition(), md.offset());

// asynchronous send (throughput) — callback is MANDATORY
producer.send(record, (metadata, ex) -> {
    if (ex != null) {
        log.error("publish failed key={}", key, ex);
        outbox.markFailed(id, ex);        // don't let it disappear silently
    } else {
        outbox.markProcessed(id);
    }
});
```

```go
// sarama - synchronous producer
cfg := sarama.NewConfig()
cfg.Producer.RequiredAcks = sarama.WaitForAll
cfg.Producer.Idempotent = true
cfg.Net.MaxOpenRequests = 1               // must be 1 when idempotent in sarama
cfg.Producer.Return.Successes = true
cfg.Producer.Compression = sarama.CompressionLZ4

producer, err := sarama.NewSyncProducer([]string{"localhost:9092"}, cfg)
_, _, err = producer.SendMessage(&sarama.ProducerMessage{
    Topic: "order.payment.requested",
    Key:   sarama.StringEncoder(orderID),
    Value: sarama.ByteEncoder(payload),
})
```

```go
// segmentio/kafka-go - writer
w := &kafka.Writer{
    Addr:         kafka.TCP("localhost:9092"),
    Topic:        "order.payment.requested",
    Balancer:     &kafka.Hash{},          // hash by key
    RequiredAcks: kafka.RequireAll,
    BatchTimeout: 10 * time.Millisecond,
    Compression:  kafka.Snappy,
    Async:        false,                  // false = errors can be handled
}
err := w.WriteMessages(ctx, kafka.Message{
    Key: []byte(orderID), Value: payload,
})
```

| Property | Default | Advice |
| :--- | :--- | :--- |
| `acks` | `all` (3.x) | don't lower it |
| `enable.idempotence` | `true` (3.x) | leave it true |
| `retries` | `MAX` | leave it |
| `delivery.timeout.ms` | 120000 | total budget for retries + requests |
| `linger.ms` | 5 | 5–20 ms for requests, 50–100 for batching |
| `batch.size` | 16 KiB | 32–64 KiB for throughput |
| `compression.type` | `none` | `lz4` (fast) / `zstd` (most economical) |
| `buffer.memory` | 32 MiB | raise it if you see `RecordTooLarge`/`TimeoutException` |
| `max.in.flight` | 5 | 5 is only safe with idempotence |

| Producer error | Meaning | Action |
| :--- | :--- | :--- |
| `TimeoutException` (batch expired) | broker slow / buffer full | raise `delivery.timeout.ms`, check the network |
| `RecordTooLargeException` | exceeds `max.request.size` / broker `max.message.bytes` | split the payload, raise both |
| `NetworkException` | connection dropped | retried automatically; check DNS/firewall |
| `NotEnoughReplicasException` | ISR < `min.insync.replicas` | **do not** lower acks; restore the replicas |
| `SerializationException` | serializer failed | validate the payload before sending |
| `OutOfOrderSequenceException` | idempotence state corrupted (rare) | the producer resets itself; log it |

> **Pitfall:** the `Hash` balancer **requires a key**. If `Key` is empty, all events land in
> random partitions → ordering between orders is lost.

## Consumer groups & rebalance

```java
// Spring Kafka - manual ack
@KafkaListener(
    topics = "order.payment.requested",
    groupId = "payment-bridge",
    concurrency = "3-6",              // threads = active partitions that can be processed
    containerFactory = "kafkaListenerContainerFactory"
)
public void onPaymentRequested(ConsumerRecord<String, String> record, Acknowledgment ack) {
    try {
        bridge.handle(record.value());
        ack.acknowledge();                 // commit after success
    } catch (Exception e) {
        throw e;                           // don't ack → retry / DLQ
    }
}
```

```yaml
spring:
  kafka:
    consumer:
      group-id: payment-bridge
      auto-offset-reset: earliest
      enable-auto-commit: false        # MUST be false when using manual ack
      max-poll-records: 100
      properties:
        max.poll.interval.ms: 300000   # exceeding this = consumer removed from the group
        session.timeout.ms: 45000
        heartbeat.interval.ms: 3000
        partition.assignment.strategy: org.apache.kafka.clients.consumer.CooperativeStickyAssignor
        group.instance.id: payment-bridge-1     # static membership
    listener:
      ack-mode: manual
      type: single
```

```go
// sarama - consumer group handler
handler := consumerGroupHandler{}
group, _ := sarama.NewConsumerGroup(brokers, "payment-bridge", cfg)
for {
    if err := group.Consume(ctx, []string{"order.payment.requested"}, handler); err != nil {
        return err
    }
}

func (h consumerGroupHandler) ConsumeClaim(sess sarama.ConsumerGroupSession, claim sarama.ConsumerGroupClaim) error {
    for msg := range claim.Messages() {
        if err := process(msg.Value); err != nil {
            return err                 // session stops → the message will be redelivered
        }
        sess.MarkMessage(msg, "")      // mark as successful
    }
    return nil
}
```

| Term | Meaning |
| :--- | :--- |
| **Consumer group** | a team of consumers; each partition is held by only one member |
| **Rebalance** | the group composition changes → partitions are reassigned → processing pauses briefly |
| **Heartbeat** | missed for > `session.timeout.ms` → the member is removed |
| **`max.poll.interval.ms`** | max total time between polls; exceed it → removed |
| **`max.poll.records`** | number of records per poll — lower it if processing is slow |
| **Static membership** | `group.instance.id` → a restart doesn't trigger a full rebalance |
| **Cooperative sticky** | incremental rebalance, only the partitions that move are paused |
| **`auto.offset.reset`** | `earliest` / `latest` — only used when no offset is stored |

```bash
# see who holds which partition & the lag
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group payment-bridge --members --verbose
```

| Symptom | Cause | Fix |
| :--- | :--- | :--- |
| Consumer removed every few minutes | processing > `max.poll.interval.ms` | raise the interval / lower `max.poll.records` |
| Constant rebalance (flapping) | slow heartbeats (GC, CPU) | `session.timeout.ms` > `heartbeat`×3, check GC |
| All partitions on one consumer | other members idle/misconfigured | check `concurrency` and the member count |
| Lag doesn't go down | consumer throughput < producer | add partitions + consumers, optimize batching |

> **Pitfall:** processing a single batch longer than `max.poll.interval.ms` (default 5 minutes) → the consumer
> is considered dead, the partitions move, and **messages get processed twice**.

## Transactional outbox

The mandatory pattern for "write to the DB" + "publish to Kafka" without losing messages.

```text
1. BEGIN
2.   INSERT INTO orders (...)          -- business data
3.   INSERT INTO outbox_events (...)   -- event, same transaction
4. COMMIT
5. relay polls PENDING -> publish -> mark PROCESSED (idempotent consumer closes the duplicate gap)
```

```sql
CREATE TABLE outbox_events (
    id             BIGSERIAL PRIMARY KEY,
    aggregate_id   VARCHAR(100) NOT NULL,
    event_type     VARCHAR(100) NOT NULL,
    topic          VARCHAR(100) NOT NULL,
    event_key      VARCHAR(100),
    payload        JSONB        NOT NULL,
    status         VARCHAR(20)  NOT NULL DEFAULT 'PENDING',  -- PENDING|PROCESSED|FAILED
    attempts       INT          NOT NULL DEFAULT 0,
    last_error     TEXT,
    created_at     TIMESTAMPTZ  NOT NULL DEFAULT now(),
    published_at   TIMESTAMPTZ,
    CONSTRAINT uq_outbox_event UNIQUE (aggregate_id, event_type, payload)
);
CREATE INDEX idx_outbox_pending ON outbox_events (created_at) WHERE status = 'PENDING';
```

```sql
-- claim a batch with SKIP LOCKED: safe for several parallel relays
BEGIN;
SELECT * FROM outbox_events
 WHERE status = 'PENDING'
 ORDER BY created_at
 LIMIT 100
   FOR UPDATE SKIP LOCKED;
-- publish to Kafka (in the app), then:
UPDATE outbox_events SET status = 'PROCESSED', published_at = now() WHERE id = ANY($1);
COMMIT;
```

```go
// relay - poll a batch, publish, mark
func (r *Relay) Run(ctx context.Context) {
    ticker := time.NewTicker(3 * time.Second)
    for {
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
            events, err := r.repo.ClaimPending(ctx, 100)   // FOR UPDATE SKIP LOCKED
            if err != nil { continue }
            for _, e := range events {
                if err := r.publish(ctx, e); err != nil {
                    r.repo.MarkFailed(ctx, e.ID, err)       // retry until max attempts
                    continue
                }
                r.repo.MarkProcessed(ctx, e.ID)
            }
        }
    }
}
```

| Why outbox (instead of publishing directly) | Consequence if you get it wrong |
| :--- | :--- |
| Publish fails, business data is already committed | Events lost without an outbox |
| Publishing inside the transaction = an RPC in a DB transaction | Long transactions, locks held |
| Dual-write (DB + Kafka) | **The classic data-loss bug** |
| Relay crashes after publish, before mark | Duplicates — handled by an idempotent consumer |

| Alternative / complement | Note |
| :--- | :--- |
| CDC (Debezium) from the WAL | no relay, but needs a connector & a stable schema |
| Kafka transaction (`sendOffsetsToTransaction`) | only safe when the **offsets also live in Kafka**, not the DB |
| Outbox + Debezium | the relay becomes code-free; the complexity moves to the connector |

> **Pitfall:** a relay that does `SELECT ... LIMIT` without `FOR UPDATE SKIP LOCKED` will be processed twice
> by two parallel relays — exactly the kind of duplicate you don't need.

## Idempotency & dedup

At-least-once delivery = **duplicates are guaranteed**. Consumers must dedup.

```sql
-- consumer inbox: dedup per event
CREATE TABLE consumer_inbox (
    consumer_name VARCHAR(100) NOT NULL,
    event_id      VARCHAR(100) NOT NULL,
    processed_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (consumer_name, event_id)
);

-- in the same transaction as the business processing
INSERT INTO consumer_inbox (consumer_name, event_id)
VALUES ('payment-bridge', :eventId)
ON CONFLICT DO NOTHING;     -- 0 rows = already processed -> skip
```

```java
if (!inbox.markProcessed("payment-bridge", eventId)) {
    log.debug("duplicate event skipped id={}", eventId);
    return;                          // ack, don't process again
}
```

```java
// idempotency key on a third-party API
@PostMapping("/payments")
public PaymentResult pay(@RequestBody PayRequest req) {
    return idempotency.runOnce(req.getIdempotencyKey(), () -> gateway.charge(req));
}
```

| Layer | Mechanism |
| :--- | :--- |
| Producer | `enable.idempotence=true` → retries don't create duplicates in the broker |
| Consumer | `consumer_inbox` / a unique constraint in the same transaction |
| Domain | `idempotency_key` UNIQUE on the transaction table |
| Upstream API | `Idempotency-Key` header + result cache |

> Producer idempotence **only** prevents duplicates from retries within a single producer session.
> Redelivery caused by a rebalance/crash still has to be handled by the consumer.

## DLQ & retry

```java
@Bean
public DefaultErrorHandler errorHandler(KafkaTemplate<String, String> template) {
    DeadLetterPublishingRecoverer recoverer = new DeadLetterPublishingRecoverer(template,
        (record, ex) -> new TopicPartition(record.topic() + ".DLT", -1));   // any partition

    var backoff = new ExponentialBackOffWithMaxRetries(3);
    backoff.setInitialInterval(500);
    backoff.setMultiplier(2.0);
    backoff.setMaxInterval(5_000);

    var handler = new DefaultErrorHandler(recoverer, backoff);
    handler.addNotRetryableExceptions(IllegalArgumentException.class, JsonParseException.class);
    return handler;
}
```

```yaml
spring:
  kafka:
    listener:
      ack-mode: manual
      common-error-handler: defaultCommonErrorHandler
```

```text
DLT payload:
{
  "original_topic": "order.payment.requested",
  "original_partition": 3,
  "original_offset": 912441,
  "original_timestamp": "2026-10-21T03:12:44Z",
  "exception_fqcn": "com.example.BizException",
  "exception_message": "insufficient balance",
  "payload": { }
}
```

| Strategy | When |
| :--- | :--- |
| In-memory retry (3×, backoff) | transient errors (timeout, 503) |
| Retry topic (`*.retry.1m`) | when you need a long delay without blocking the partition |
| DLQ / DLT | permanent errors (bad schema, invalid data) |
| Combination | retry first → DLT; a DLT is **mandatory** or events vanish silently |
| Replay | after the bug is fixed, consume the DLT back into the original topic |

> **Pitfall:** a long in-memory retry blocks the partition (the next record waits).
> For delays measured in minutes, use a retry **topic**, not `Thread.sleep`.

## Ordering & keying

| Need | How |
| :--- | :--- |
| Ordering per order | `key = orderId` (partition = hash(key)) |
| Ordering per merchant | `key = merchantId` |
| Global ordering | 1 partition — throughput drops drastically |
| No ordering | `key = null` → round robin, maximum throughput |

```java
// events for the same order MUST have the same key
kafkaTemplate.send("order.payment.requested", orderId, event);
```

```java
// partitioner strategy: default murmur2 (Java) — consistent across clients
p.put(ProducerConfig.PARTITIONER_CLASS_CONFIG,
      "org.apache.kafka.clients.producer.internals.DefaultPartitioner");
```

> **Pitfall:** "ordering is guaranteed per partition", not per key. The same key sent through producers with
> different `acks`/`retries` can arrive in a different order. Also: adding partitions changes
> `hash(key) % partitions` → a key can move to another partition.

## Schema & serialization (Avro / Protobuf)

```json
// avro - order.payment.requested v2 (add a field with a default)
{
  "type": "record",
  "name": "PaymentRequested",
  "namespace": "com.example.events",
  "fields": [
    { "name": "eventId", "type": "string" },
    { "name": "orderId", "type": "string" },
    { "name": "total",   "type": "long" },
    { "name": "currency", "type": "string", "default": "IDR" }
  ]
}
```

```properties
# producer/consumer with Schema Registry
schema.registry.url=http://schema-registry:8081
value.serializer=io.confluent.kafka.serializers.KafkaAvroSerializer
auto.register.schemas=false          # production: register via CI, not automatically
use.latest.version=true
```

| Compatibility | Meaning |
| :--- | :--- |
| `BACKWARD` | new consumers can read old data (default) |
| `FORWARD` | old consumers can read new data |
| `FULL` | both — the safest for long-lived events |
| `NONE` | unrestricted (avoid on an event backbone) |

| Evolution rule | Detail |
| :--- | :--- |
| Add a field | must have a `default` |
| Remove a field | must have a `default` and not be used by consumers |
| Rename a field | use an alias, don't remove it outright |
| Change a type | **incompatible** — add a new field |
| Serializer | be consistent with Avro **or** Protobuf per topic |

> **Pitfall:** `auto.register.schemas=true` in production lets a producer write an
> incompatible schema that immediately breaks every existing consumer.

```bash
curl -s localhost:8083/connectors/orders-sink/status | jq .tasks

  --data @orders-sink.json localhost:8083/connectors/orders-sink/config
curl -s -X DELETE localhost:8083/connectors/orders-sink
```

| Mode | Example |
| :--- | :--- |
| Source | Debezium PostgreSQL (CDC from the WAL) |
| Sink | JDBC (Postgres/MySQL), S3, Elasticsearch, BigQuery |
| Transform | `SMT` (Single Message Transform): rename fields, mask PII, route topics |
| Conversion | Avro/JSON Schema + Schema Registry |

| Rule | Why |
| :--- | :--- |
| `insert.mode=upsert` + `pk.mode` | Kafka duplicates don't duplicate rows |
| `errors.tolerance=all` + DLQ | don't stop the sink just because of 1 bad record |
| `tasks.max` ≤ partition count | more tasks = idle |
| `auto.create=false` | silent DDL in production is dangerous |

> **Pitfall:** a sink connector that isn't upsert (insert-only) will duplicate rows every time the
> consumer lag is reset or an event is replayed.

## Kafka Streams & ksqlDB

```java
StreamsBuilder b = new StreamsBuilder();

KStream<String, PaymentRequested> payments = b.stream("order.payment.requested",
        Consumed.with(Serdes.String(), paymentSerde));

// windowed aggregation: total per merchant per 5 minutes
KTable<Windowed<String>, Long> perMerchant = payments
    .groupBy((k, v) -> v.merchantId(), Grouped.with(Serdes.String(), paymentSerde))
    .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(5)))
    .count(Materialized.as("payments-count-store"));

perMerchant.toStream().to("merchant.payment.count", Produced.with(
        WindowedSerdes.timeWindowedSerdeFrom(String.class), Serdes.Long()));

// stream-table join
KTable<String, Order> orders = b.table("orders", Consumed.with(Serdes.String(), orderSerde));
payments.join(orders, (p, o) -> new Enriched(p, o)).to("enriched.topic");

KafkaStreams streams = new KafkaStreams(b.build(), props);
streams.start();
Runtime.getRuntime().addShutdownHook(new Thread(streams::close));
```

```properties
application.id=payment-analytics
processing.guarantee=exactly_once_v2      # idempotent writes to the output topic
num.stream.threads=3
default.key.serde=org.apache.kafka.common.serialization.Serdes$StringSerde
state.dir=/var/lib/kafka-streams
```

| Concept | Note |
| :--- | :--- |
| `KStream` vs `KTable` | stream = event, table = state per key |
| `GlobalKTable` | replicated to every instance (small lookups) |
| State store | local + changelog topic; restored on rebalance |
| Exactly-once (`exactly_once_v2`) | against the output topic, not external side effects |
| `ksqlDB` | streaming SQL: `CREATE STREAM`, `EMIT CHANGES`, push queries |

> **Pitfall:** `processing.guarantee=exactly_once_v2` does **not** make HTTP calls inside
> `peek/forEach` idempotent. External side effects still need an idempotency key.

## Operations: upgrades, rolling restart, disk full

```bash
# rolling restart (no downtime, but protect the ISR)
for b in 2 1 0; do
  ssh broker$b 'systemctl restart kafka'
  until kafka-broker-api-versions.sh --bootstrap-server broker$b:9092 >/dev/null 2>&1; do sleep 5; done
  sleep 30                                    # wait for the ISR to be full again
  kafka-topics.sh --bootstrap-server broker0:9092 --describe --under-replicated-partitions
done
```

| Event | Steps |
| :--- | :--- |
| Disk almost full | lower per-topic `retention.bytes`, delete old segments, add brokers + reassign |
| Leader dies | another broker takes over leadership (seconds) — make sure RF ≥ 3 |
| Consumer lag spikes | add partitions **only if** ordering isn't critical; scale consumers first |
| Need to reset a group | make sure all consumers are stopped; reset; start again |
| Need a version upgrade | upgrade clients first (compatible), then the brokers rolling; KRaft: **never** roll `log.message.format.version` back |

> **Pitfall:** a full disk on one broker = replicas fail, the ISR shrinks, `acks=all` starts
> failing → **producer errors across the whole cluster**. Alerting on `disk_free < 20%` is mandatory.

| Rule | Why |
| :--- | :--- |
| `ssl.client.auth=required` | clients without a certificate are rejected |
| `allow.everyone.if.no.acl.found=false` | default-deny (don't leave it open) |
| ACL per principal per topic | least privilege, not a shared user |
| Minimal `super.users` | super users bypass every ACL |
| `SCRAM-SHA-512` | mTLS is fine, but SASL makes rotation easier |

> **Pitfall:** enabling the `authorizer` on a cluster that already has many consumers without ACLs
> means every consumer immediately gets `TopicAuthorizationException`. Set up the ACLs first, then enable it.

## Pitfalls (must read)

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| `acks=1` | Data lost when the leader dies | `acks=all` + `min.insync.replicas=2` |
| Dual-write DB + Kafka without an outbox | Events lost | Transactional outbox (+ SKIP LOCKED) |
| `enable-auto-commit=true` | Offset committed before processing finishes | `false` + manual ack after success |
| `max.poll.interval.ms` < processing time | Consumer kicked, messages processed 2× | Raise the interval / lower `max.poll.records` |
| Retry without idempotency | Double debit | Idempotency key + unique constraint |
| Empty key on the producer | Ordering lost, uneven partitions | Always set a key |
| Adding partitions on keyed topics | Per-key ordering breaks | Don't add if ordering is critical; create a new topic |
| Too many partitions | Slow metadata & rebalance | < 10,000 partitions per cluster |
| Topic without retention | Disk full | `retention.ms` + `retention.bytes` |
| DLQ without alerts | Messages vanish silently | Metrics + DLQ depth alert |
| Non-idempotent consumer during rebalance | Double effects | `consumer_inbox` |
| `linger.ms` too high | Latency climbs | 5–20 ms for requests |
| Long in-memory retry | Partition blocked | Retry topic with a delay |
| `auto.register.schemas=true` | Broken schema for old consumers | Register via CI, `false` |
| Insert-only sink connector | Duplicate rows after replay | `upsert` + `pk.mode` |
| Hot partition | One consumer overwhelmed | Bucketed key (e.g. `merchantId#bucket`) |
| Consumer only runs on start | Offsets never committed | Explicit commit / `ack-mode: manual` |
| Resetting offsets while consumers are alive | Data processed twice / group conflict | Stop the consumers first |
